# ContainerStack ecosystem integration bar

**Research date:** 2026-08-11. Live documentation and `main` branches were read on this date; where a source exposes a release/build date it is recorded below. The product under design is **ContainerStack**, its daemon is **containerstackd**, and its CLI is **cstack**. “Apple Container” means `github.com/apple/container`; “Containerization” means `github.com/apple/containerization`.

## Executive finding

A Docker-compatible HTTP API is necessary but not sufficient. The easiest consumers are clients that only invoke the Docker CLI/API for ordinary CRUD. The practical compatibility cliff is the combination of socket discovery, Docker API metadata/version behavior, build sessions (BuildKit), nested/privileged containers, VM path mapping, and Docker-specific network/stream/cleanup semantics. ContainerStack should ship a stable Unix socket and `DOCKER_HOST`/Docker-context integration, then implement a tested Docker Engine API compatibility profile rather than claiming “Docker compatible” from a few CRUD endpoints.

## Per-consumer detail

### 1. Testcontainers (Java, Go, Node, Python)

**Discovery and configuration (OBSERVED).** Java’s `DockerClientProviderStrategy` source documents and enforces this order: `TestcontainersHostPropertyClientProviderStrategy`, `EnvironmentAndSystemPropertyClientProviderStrategy`, a persisted strategy in `~/.testcontainers.properties`, then all other strategies by priority. The environment strategy itself resolves `DOCKER_HOST` first and then `docker.host` in the user properties. [Java strategy source](https://raw.githubusercontent.com/testcontainers/testcontainers-java/main/core/src/main/java/org/testcontainers/dockerclient/DockerClientProviderStrategy.java) (live `main`, accessed 2026-08-11); [environment strategy source](https://raw.githubusercontent.com/testcontainers/testcontainers-java/main/core/src/main/java/org/testcontainers/dockerclient/EnvironmentAndSystemPropertyClientProviderStrategy.java) (live `main`, accessed 2026-08-11).

**Configuration files and socket overrides (OBSERVED).** Java docs load environment variables first, then `~/.testcontainers.properties`, then classpath `testcontainers.properties` (with deterministic classpath conflict rules). `DOCKER_HOST` controls the client endpoint; `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE` is a separate host socket path used by Ryuk, Compose and helper containers; `TESTCONTAINERS_HOST_OVERRIDE` changes the host address used for exposed ports. Ryuk is privileged by default; if the runtime cannot start privileged containers, `TESTCONTAINERS_RYUK_DISABLED=true` is the documented escape hatch. [Java configuration docs](https://java.testcontainers.org/features/configuration/) (live docs, accessed 2026-08-11).

**Runtime-specific workarounds (OBSERVED).** The Java supported-runtime page says alternatives are not actively tested in the main workflow. Colima requires `colima start --network-address`, `DOCKER_HOST=unix://${HOME}/.colima/default/docker.sock`, `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`, and `TESTCONTAINERS_HOST_OVERRIDE=$(colima ls -j | jq -r '.address')`. Podman macOS requires `DOCKER_HOST` from `podman machine inspect` plus the socket override; rootless Podman requires disabling Ryuk. [Supported runtime docs](https://java.testcontainers.org/supported_docker_environment/) (live docs, accessed 2026-08-11).

**Go discovery (OBSERVED).** Testcontainers Go’s current configuration docs give an explicit order: `tc.host` in `~/.testcontainers.properties`, `DOCKER_HOST`, a Go context value carrying `DOCKER_HOST` (used internally for the reaper), `/var/run/docker.sock`, then `docker.host` in the properties file, then rootless socket paths (`$XDG_RUNTIME_DIR/.docker/run/docker.sock`, `$HOME/.docker/run/docker.sock`, `$HOME/.docker/desktop/docker.sock`, `/run/user/$UID/docker.sock`). The same page documents `TESTCONTAINERS_RYUK_CONTAINER_PRIVILEGED`, `TESTCONTAINERS_RYUK_DISABLED`, and `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE`. [Go configuration docs](https://golang.testcontainers.org/features/configuration/) (live docs, accessed 2026-08-11).

**Node and Python (OBSERVED).** Testcontainers Node 12.1.0’s package declares `dockerode`, `docker-compose`, and `ssh-remote-port-forward` dependencies; its README documents `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE`, `TESTCONTAINERS_RYUK_PRIVILEGED`, `TESTCONTAINERS_RYUK_DISABLED`, `RYUK_CONTAINER_IMAGE`, and reconnection timeout controls. [Node package.json](https://raw.githubusercontent.com/testcontainers/testcontainers-node/main/packages/testcontainers/package.json) (version 12.1.0 in live `main`, accessed 2026-08-11); [Node README](https://raw.githubusercontent.com/testcontainers/testcontainers-node/main/README.md) (copyright 2018–2025, live `main`, accessed 2026-08-11). Python’s current `DockerClient` wrapper obtains `tc_host` from the Testcontainers properties or `DOCKER_HOST`, sets `DOCKER_HOST`, then calls `docker.from_env()`; the official README documents socket override, Ryuk privileged/disabled flags, image and timeout controls. [Python client source](https://raw.githubusercontent.com/testcontainers/testcontainers-python/master/core/testcontainers/core/docker_client.py) (live `master`, accessed 2026-08-11); [Python README](https://raw.githubusercontent.com/testcontainers/testcontainers-python/main/README.md) (live `main`, accessed 2026-08-11).

**Docker contexts (OBSERVED/INFERRED).** The Java strategy source contains no `DOCKER_CONTEXT` strategy: its explicit inputs are `DOCKER_HOST`, TLS variables, Testcontainers properties and Docker Machine/provider strategies. [OBSERVED] Docker CLI contexts can still be made to work by exporting the context’s endpoint as `DOCKER_HOST` or using a Docker socket/context that the underlying Docker client understands. [INFERRED] ContainerStack should provide a normal Docker CLI context and a stable endpoint, but should not assume every Testcontainers language binding reads contexts itself.

**API/feature bar (INFERRED from documented behavior and Docker Engine API).** Minimum practical calls are `/_ping`, `/version`, `/info`; image pull/list/remove; `POST /containers/create`, start/stop/kill/remove, inspect; exec create/start/resize; logs/attach; network and volume create/remove; port inspection and event/stream handling. Ryuk additionally needs to create a privileged helper, mount or otherwise reach the daemon socket, and list/remove resources by Testcontainers labels. A successful ping with missing port publication or host reachability is not sufficient.

**ContainerStack implication.** Ship an opt-in `containerstackd` socket endpoint plus a cstack-created Docker context; implement the Testcontainers startup checks, resource labels/filters, hijacked exec/attach streams, and socket override semantics. If ContainerStack cannot support a privileged sidecar, document Ryuk-disabled mode and provide daemon-side session cleanup.

### 2. VS Code Dev Containers and Container Tools

**Dev Containers CLI (OBSERVED).** The official CLI README’s `devcontainer up` transcript shows it launching `docker build`, then `docker run --sig-proxy=false ... --mount ... --cap-add=SYS_PTRACE --security-opt seccomp=unconfined ...`, and `devcontainer exec` for lifecycle commands. [Dev Containers CLI README](https://raw.githubusercontent.com/devcontainers/cli/main/README.md) (live `main`, accessed 2026-08-11). This is shell-out integration: the CLI itself does not need a bespoke HTTP client if a compatible `docker`/`podman` executable is on `PATH`; that executable talks to the socket/API.

**Container Tools extension (OBSERVED).** Microsoft’s runtime-client package explicitly says it abstracts “the runtime and the way it is called” and that each runtime client contributes a command line plus an output parser; its example calls `DockerClient.inspectContainers()` through a shell command runner. The extension README requires Docker installed/on `PATH`, documents Docker or Podman clients via `containers.containerClient` and `containers.orchestratorClient`, and lists image/network/volume/registry/Compose commands. [Runtime client README](https://raw.githubusercontent.com/microsoft/vscode-containers/main/packages/vscode-container-client/README.md) (live `main`, accessed 2026-08-11); [Container Tools README](https://raw.githubusercontent.com/microsoft/vscode-containers/main/extensions/vscode-containers/README.md) (live `main`, accessed 2026-08-11).

**Hard behavior and breakage (INFERRED).** The daemon must accept the CLI’s build/run/exec/inspect/remove flags, bind mounts, labels, capabilities and security options; support Compose if the user chooses Compose commands; and make host paths visible inside its VM. Non-Docker daemons commonly fail after connection because flags or inspect JSON differ, a path is not shared into the VM, BuildKit features are missing, or stream/exit-code handling differs. ContainerStack can reduce friction by shipping `cstack` as a Docker-compatible executable/provider and a VS Code setting/provider that avoids pretending Apple’s native `container` CLI is Docker.

### 3. JetBrains Docker plugin

**Connection modes (OBSERVED).** JetBrains documents explicit Docker Engine API access and connection modes: Docker for Windows/Mac, Unix socket, TCP socket (including custom Unix socket paths), SSH, WSL and Minikube. It can add connections from configured Docker contexts. It also lets users specify Docker CLI and standalone Compose executable paths; the remote-server prerequisites call out Docker CLI and Docker Buildx for Dockerfile builds. [Docker docs](https://www.jetbrains.com/help/idea/docker.html) (built 2026-08-04; page dated 8 April 2026); [connection settings](https://www.jetbrains.com/help/idea/settings-docker.html) (built 2026-08-04; page dated 24 February 2026).

**Podman precedent (OBSERVED).** JetBrains has a dedicated Podman page: it treats Podman’s API as Docker-equivalent, asks users to select a Podman machine, and directs users to the API socket/`DOCKER_HOST`; it also calls out a distinct “executable found, connection to Podman socket failed” troubleshooting path. [Podman docs](https://www.jetbrains.com/help/idea/podman.html) (built 2026-08-04; page dated 5 February 2026).

**API/feature bar and breakage (INFERRED).** IDE operations require more than listing containers: inspect JSON, image pull/push/build, Compose project operations, logs/exec/attach, registry auth, ports, volume mounts and Buildx. On macOS, JetBrains rewrites local paths through configured VM mappings; a native daemon that does not expose equivalent shared-path semantics will make bind mounts fail even when the socket connection is green. A ContainerStack-specific connection profile or Docker context would be a low-friction adoption path.

### 4. BuildKit and buildx

**Builder topology (OBSERVED).** Docker’s BuildKit docs say BuildKit is the default builder for Docker Desktop and Docker Engine. Docker buildx’s driver docs specify: `docker` uses the BuildKit library bundled into the Docker daemon; `docker-container` creates a dedicated BuildKit container; `kubernetes` creates BuildKit pods; and `remote` connects directly to a manually managed `buildkitd`. [BuildKit docs](https://docs.docker.com/build/buildkit/) (live docs, accessed 2026-08-11); [build drivers](https://docs.docker.com/build/builders/drivers/) (live docs, accessed 2026-08-11).

**Can a foreign daemon satisfy `docker build`? (INFERRED with observed constraints.)** Yes for basic builds only if the selected buildx `docker` driver can call a compatible Engine image-build endpoint and the daemon supplies the expected BuildKit backend/session behavior. A daemon that merely implements container CRUD cannot satisfy modern `docker build`; the client expects build progress streams, cache/export behavior and BuildKit features. Setting legacy `DOCKER_BUILDKIT=0` can sometimes use the old builder path, but that is a fallback with a shrinking feature set, not a substitute for BuildKit.

**nerdctl and Podman (OBSERVED).** nerdctl’s official build guide says `nerdctl build` relies on BuildKit and requires a configured `buildkitd`, either with a containerd worker or OCI worker; `--buildkit-host`/`BUILDKIT_HOST` select the BuildKit socket and defaults are tried in a defined order. Podman’s build docs say `podman build` uses Buildah; `podman buildx build` is an alias of `podman build` and “not all buildx build features are available.” [nerdctl BuildKit guide](https://raw.githubusercontent.com/containerd/nerdctl/main/docs/build.md) (live `main`, accessed 2026-08-11); [Podman build docs](https://docs.podman.io/en/latest/markdown/podman-build.1.html) (live docs, accessed 2026-08-11).

**ContainerStack implication.** Treat `containerstackd`’s Docker image-build endpoint and a BuildKit service as separate compatibility surfaces. The lowest-risk design is a documented remote BuildKit builder (`cstack buildx create --driver remote …`) or a bundled BuildKit worker, with explicit image-store import/export semantics. Do not claim buildx compatibility from implementing `/build` alone.

### 5. kind, k3d and minikube

**kind (OBSERVED).** kind’s current quick start says it auto-detects Docker, Podman or nerdctl, with `KIND_EXPERIMENTAL_PROVIDER` overrides. Its rootless guide supports Docker, Podman and nerdctl but requires cgroup v2 and cgroup-controller delegation; it documents iptables module requirements, PID limits, inotify limits, privileged-port restrictions and rootless filesystem restrictions. [kind quick start](https://kind.sigs.k8s.io/docs/user/quick-start/#creating-a-cluster) (current docs/release v0.32.0, accessed 2026-08-11); [kind rootless guide](https://kind.sigs.k8s.io/docs/user/rootless/) (current docs, accessed 2026-08-11).

**k3d (OBSERVED).** k3d documents Podman v4+ as compatible but explicitly experimental. It requires a Podman API socket, `DOCKER_HOST` and `DOCKER_SOCK`; rootless macOS uses a Podman machine and requires cgroup delegation. It calls out CPU/CPUSET/I/O delegation, Podman’s DNS-disabled default network, explicit registry network selection and incompatibility with `--registry-create` assuming Docker’s `bridge`. [k3d Podman guide](https://raw.githubusercontent.com/k3d-io/k3d/main/docs/usage/advanced/podman.md) (live `main`, accessed 2026-08-11).

**minikube (OBSERVED).** The Docker driver requires Docker 18.09+ (20.10 recommended), supports amd64/arm64 and has rootless requirements for cgroup v2 delegation and modern kernel overlayfs. The Podman driver is explicitly experimental, recommends CRI-O (or containerd for rootless), and on macOS requires a Podman VM. [Docker driver](https://minikube.sigs.k8s.io/docs/drivers/docker/) (modified 25 July 2026); [Podman driver](https://minikube.sigs.k8s.io/docs/drivers/podman/) (modified 5 April 2023).

**ContainerStack implication (INFERRED).** A Docker-API shim is insufficient for these tools. Apple Container’s Linux VM must expose the kernel/cgroup/mount/network/privileged behavior required by a Kubernetes node container, or ContainerStack should position itself as the runtime *inside* a VM rather than promise kind/k3d/minikube support. This is High difficulty and should be an explicit compatibility tier.

### 6. CI runners: act and GitLab Runner

**act (OBSERVED).** act’s official README says it uses the Docker API to pull/build images and run containers for each action. Its current CLI source exposes `--container-daemon-socket` (“URI to Docker Engine socket”, with `-` disabling socket bind mounting), `--container-architecture` (requires Docker server API v1.41+), `--privileged`, `--network` (default `host`), capability controls, and `--container-options`. [act README](https://raw.githubusercontent.com/nektos/act/master/README.md) (live `master`, accessed 2026-08-11); [act CLI source](https://raw.githubusercontent.com/nektos/act/master/cmd/root.go) (live `master`, accessed 2026-08-11).

**GitLab Runner (OBSERVED).** GitLab’s Docker executor uses Docker Engine to run isolated job containers and services, supports macOS hosts, and documents that it uses Docker Engine API v1.25. Its network-per-build mode creates a user-defined bridge network; runner configurations include privileged mode and volumes. [GitLab Docker executor](https://docs.gitlab.com/runner/executors/docker/) (GitLab Docs 19.3, page current in 2026, accessed 2026-08-11).

**Breakage and ContainerStack implication (INFERRED).** CI workflows frequently run a Docker CLI inside the job and mount the outer socket, or start Docker-in-Docker. ContainerStack therefore needs a socket path that is mountable into job containers, correct API version negotiation, image build/load, service networks, privileged/cgroup support and architecture handling. A rootless or no-nested-container mode should be advertised as “simple jobs only.”

### 7. Docker Compose v2 binary

**Implementation (OBSERVED).** The official Compose repository describes the binary as the `docker compose` tool and its current `go.mod` depends directly on `github.com/docker/cli`, `github.com/moby/moby/api`, `github.com/moby/moby/client`, `github.com/docker/buildx`, and `github.com/moby/buildkit`. [Compose README](https://raw.githubusercontent.com/docker/compose/main/README.md) (live `main`, accessed 2026-08-11); [Compose go.mod](https://raw.githubusercontent.com/docker/compose/main/go.mod) (live `main`; includes Compose v5 module, Docker CLI 29.6.2, Moby API 1.55.0, buildx 0.36.0 and BuildKit 0.32.1 at research time, accessed 2026-08-11).

**Foreign daemon behavior (OBSERVED/INFERRED).** Compose is a client of the Docker Engine API, so the official binary can drive a foreign daemon when `DOCKER_HOST`/context reaches a socket and the daemon implements the endpoints/features Compose calls. Podman’s current API-service docs explicitly describe a Docker v1.40 compatibility layer and show `DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock; docker-compose up`. Podman’s `podman compose` is only a thin wrapper around an external provider; it prefers `docker-compose` when installed and passes the command through. [Podman API service](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html) (current docs; history notes original January 2020, accessed 2026-08-11); [Podman Compose wrapper](https://docs.podman.io/en/latest/markdown/podman-compose.1.html) (current docs, accessed 2026-08-11).

**Common failure modes (INFERRED from those contracts).** Socket activation timeout or wrong path; API version/metadata differences; Docker bridge/DNS/host-gateway assumptions; project labels and filtering; bind/volume path translation; BuildKit/buildx; health/depends-on and attach/logs/exec stream behavior; options not implemented by a foreign API. The fact Podman exposes a *versioned compatibility layer* rather than the whole Docker API is the right precedent for ContainerStack: publish a versioned support matrix and fail clearly on unsupported Compose features.

## Top 10 things that break a “Docker-compatible” daemon in practice

Ranked by how often they are exposed across the sources above and by blast radius. Each item is an evidence-backed integration test target.

1. **Socket discovery, endpoint schemes and socket propagation.** Clients disagree about `DOCKER_HOST`, properties, contexts and fallback paths; helper/job containers may need the host socket mounted at `/var/run/docker.sock`. Testcontainers’ separate socket override and Podman’s `DOCKER_HOST` instructions are direct evidence. [Testcontainers config](https://java.testcontainers.org/features/configuration/), [Podman service](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html), [act source](https://raw.githubusercontent.com/nektos/act/master/cmd/root.go).
2. **Version/metadata negotiation, not just HTTP reachability.** Libraries probe `/_ping`, `/version` and `/info`, branch on API/server version, and may require minimum API versions (act’s architecture flag requires v1.41; GitLab documents v1.25). Podman exposes a Docker v1.40 compatibility layer and does not reject unsupported versions, illustrating why metadata can be misleading. [act source](https://raw.githubusercontent.com/nektos/act/master/cmd/root.go), [GitLab Runner](https://docs.gitlab.com/runner/executors/docker/), [Podman service](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html).
3. **BuildKit/buildx and build session semantics.** Modern `docker build` assumes BuildKit; buildx has separate drivers and cache/export/multi-platform behavior. nerdctl explicitly needs buildkitd; Podman’s buildx alias lacks full feature parity. [Build drivers](https://docs.docker.com/build/builders/drivers/), [nerdctl build](https://raw.githubusercontent.com/containerd/nerdctl/main/docs/build.md), [Podman build](https://docs.podman.io/en/latest/markdown/podman-build.1.html).
4. **Privileged/nested containers and cgroup delegation.** Ryuk needs privileged mode; kind/k3d/minikube run Kubernetes nodes inside containers and require cgroup v2/controller delegation, mounts and often privileged operations. [Testcontainers config](https://java.testcontainers.org/features/configuration/), [kind rootless](https://kind.sigs.k8s.io/docs/user/rootless/), [k3d Podman](https://raw.githubusercontent.com/k3d-io/k3d/main/docs/usage/advanced/podman.md).
5. **Network topology, bridge names, DNS and host/port reachability.** Testcontainers needs a host override; k3d documents Podman’s missing/default-DNS network and registry-network differences; GitLab’s network-per-build relies on user-defined bridge behavior. [Testcontainers runtime](https://java.testcontainers.org/supported_docker_environment/), [k3d Podman](https://raw.githubusercontent.com/k3d-io/k3d/main/docs/usage/advanced/podman.md), [GitLab Runner](https://docs.gitlab.com/runner/executors/docker/).
6. **Bind mounts and VM path mapping.** Docker-for-Mac/Podman-machine/Apple-VM paths are not interchangeable. JetBrains explicitly forbids mounts outside configured shared roots; Dev Containers passes host paths into `docker run`; Testcontainers’ socket override is itself a mount workaround. [JetBrains settings](https://www.jetbrains.com/help/idea/settings-docker.html), [Dev Containers CLI](https://raw.githubusercontent.com/devcontainers/cli/main/README.md), [Testcontainers config](https://java.testcontainers.org/features/configuration/).
7. **Image-store, registry and platform behavior.** Buildx and minikube workflows rely on image load/import, registry auth and multi-platform manifests; act exposes architecture selection; Podman’s build path and Containerd/nerdctl stores are not the same as Docker’s image store. [Build drivers](https://docs.docker.com/build/builders/drivers/), [act source](https://raw.githubusercontent.com/nektos/act/master/cmd/root.go), [minikube Docker driver](https://minikube.sigs.k8s.io/docs/drivers/docker/).
8. **Hijacked/streaming exec, attach, logs and events.** Testcontainers, IDEs, Compose and CI all need interactive exec/attach, log follow and reliable exit/status framing; an API returning correct JSON for CRUD can still hang or corrupt multiplexed streams. [Testcontainers Java strategy](https://raw.githubusercontent.com/testcontainers/testcontainers-java/main/core/src/main/java/org/testcontainers/dockerclient/DockerClientProviderStrategy.java), [Compose go.mod](https://raw.githubusercontent.com/docker/compose/main/go.mod), [act README](https://raw.githubusercontent.com/nektos/act/master/README.md).
9. **Resource cleanup, labels/filters and lifecycle races.** Ryuk depends on labels and privileged cleanup; Compose project isolation and CI cleanup depend on force-remove, volume/network deletion and event timing. A daemon that only stops the happy-path container leaves leaked resources and flaky suites. [Testcontainers configuration](https://java.testcontainers.org/features/configuration/), [Go Testcontainers config](https://golang.testcontainers.org/features/configuration/), [Podman Compose](https://docs.podman.io/en/latest/markdown/podman-compose.1.html).
10. **Docker-specific CLI/plugin semantics (Compose, contexts, capabilities and security flags).** Dev Containers and Container Tools shell out to Docker commands; JetBrains may invoke Docker CLI/Compose/Buildx; Compose itself embeds Docker CLI/buildx/buildkit dependencies. Supporting an HTTP endpoint while omitting CLI plugin discovery, `docker compose`, context metadata, `--cap-add`, `--security-opt`, or clear unsupported-feature errors produces “connects but unusable” integrations. [Dev Containers CLI](https://raw.githubusercontent.com/devcontainers/cli/main/README.md), [Container Tools](https://raw.githubusercontent.com/microsoft/vscode-containers/main/extensions/vscode-containers/README.md), [JetBrains settings](https://www.jetbrains.com/help/idea/settings-docker.html), [Compose go.mod](https://raw.githubusercontent.com/docker/compose/main/go.mod).

## Implications for ContainerStack

1. **Ship a first-class Docker endpoint.** `containerstackd` should expose a stable Unix socket, `DOCKER_HOST` support, and a cstack-created Docker context. Do not require users to symlink an arbitrary socket into `/var/run/docker.sock`; offer an explicit compatibility setup command.
2. **Publish a versioned API profile.** Start with `/version`, `/_ping`, `/info`, image/container lifecycle, exec/attach/logs, networks, volumes, ports, events and auth. Test against Docker Engine API versions used by Testcontainers, act and GitLab Runner, and return coherent metadata.
3. **Separate BuildKit from runtime claims.** Either embed BuildKit or provide a documented remote BuildKit endpoint and image import/export path. Do not advertise buildx until cache, session, multi-platform and `--load` behavior are tested.
4. **Treat nested Kubernetes and Docker-in-Docker as a separate tier.** kind/k3d/minikube and CI workflows need cgroups, privileged operations, mounts and network behavior that a thin API shim cannot provide. On Apple Silicon, explicitly document Linux VM and Rosetta/architecture limits.
5. **Make host-path and network behavior explicit.** Provide daemon-visible path mapping, host-gateway/port discovery and stable user-defined networks; add compatibility tests for Compose, Testcontainers and Dev Containers.
6. **Provide graceful degradation.** Expose a machine-readable unsupported-feature response and docs for Ryuk-disabled, no-privileged and no-nested-container modes. “Docker-compatible” should mean a tested profile, not an unbounded promise.
